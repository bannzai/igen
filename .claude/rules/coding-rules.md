# コーディングルール（一般）

このドキュメントは、igen プロジェクト全体（iOS）に適用される一般的なコーディングルールを定義します。

## 基本原則

- コーディング規約から逸脱したい場合はコメントに理由を書いてください
- **コードの読みやすさを優先する**
- **宣言的なスタイルを使用する**: 手続き的なコードよりも宣言的なコードを優先する
- **関数は冪等にする**: 冪等にできない理由がある場合はコメントで理由を明記する
- **パフォーマンス最適化は基本的に考慮しない。コードの読みやすさを優先する**
  - 例外: 100件を超える件数を扱う場合や、bodyから表示のための計算で数十件のデータを都度計算しているパターンでは最適化を考慮する
  - 星空背景などの常時アニメーションを伴う描画処理はこの例外に該当する

## インデントとフォーマット

- インデントはtab(=2space)にしてください。Xcode標準のtab(=4space)ではありません
- 標準型の拡張ファイルは `{TypeName}+.swift` のような命名にする（例: `DateInterval+.swift`, `String+.swift`）
  - 1つの型に対して1つの拡張ファイルを使用し、ファイル内で複数の拡張がある場合は `// MARK: -` を使って機能ごとにセクション分けする

## guard と if の使い分け

- **`guard` は関数の事前条件にのみ使用する**
  - 関数の引数チェック、必須パラメータの検証など、その関数が実行できる前提条件を確認する場合に使用
- **`if` はロジックに関わる条件すべてに使用する**
  - データの検証、フィルタリング、ビジネスロジックの分岐など、ロジックに関わる条件判定には `if` を使用
  - ループ内で `continue` や `break` を使う場合でも、ロジック条件であれば `if` を使用する（`guard ... else { continue }` は使わない）
- 理由: `guard` と `if` が入り混じると読みづらくなる。ロジックに関わる箇所は全て `if` で表現することで、コードの一貫性と可読性が向上する

### guard/if 文は1行で書かない

- `guard let ... else { return }` や `if let ... { ... }` を1行にまとめて書かない
- 条件部分、else句（guardの場合）、本体（ifの場合）はそれぞれ別の行に分ける

## コメントの書き方

### プロパティのコメントは横ではなく上に書く

enumのケースやプロパティの説明コメントは、同じ行ではなく上の行に記載する

### コメントには具体的な数値を書かない

- コードに書いてある具体的な数値はコードを見ればわかるので、コメントには書かない
- コメントには「何を調整しているか」「どのような意図か」を書く

## Calendar と Locale

- **Calendar と Locale は `.current` ではなく `.autoupdatingCurrent` を使用する**
  - `.current` はインスタンス作成時の設定を保持し続けるため、アプリ実行中にユーザーがシステム設定を変更しても反映されない

## 現在時刻

- 現在時刻が必要な場合は `Date()` ではなく `Date.now` を使用する

## 状態とプロパティの宣言

- 状態の宣言は最小限に
  - 特定の値が存在する場合、特定の値がどのようになっているかを考えて重複した意味にならないかを十分に検討してください
  - 特にonChange(of) を使用して状態を更新している場合は疑った方が良いです
- **記述が短くなる、という理由だけで変数やプロパティを宣言しない**
  - 変数・プロパティは意味のある抽象化や再利用のために宣言する
  - 1回しか使わない値を変数に入れるのは避ける。直接使用する方が明確
- **ただ関数を呼ぶだけの computed property（getter）を作らない**
  - 関数を1回呼ぶだけのラッパー getter は宣言せず、関数を直接呼び出す
  - 同じ値を複数回参照して二重計算を避けたい場合は、`body` 等の中でローカル `let` に束縛する（getter は作らない）

## Equatable と Hashable

- **Equatable と Hashable の実装は極力定義しない**
  - SwiftのコンパイラはEquatableとHashableの実装を自動合成できる
  - 手動実装が必要な場合（パフォーマンス最適化、特定プロパティのみで比較など）は、コメントで理由を明記する

## デフォルト引数

- **デフォルト引数は複数の使用パターンがある場合にのみ使用する**

## データの所有と計算ロジック

### データの所有者が計算責任を持つ

- あるデータから派生する計算ロジックは、そのデータを所有する型が責任を持つべき
- computed property を使って、派生データの計算ロジックを所有者に集約する
- 使用側で毎回同じ計算ロジックを書くのは DRY 原則に反する

### Single Source of Truth

- 同じ計算ロジックが複数箇所に散在するのは保守性を下げる
- computed property や関数として1箇所に定義し、他の場所から参照する

### ロジックの重複を無理に共通化しない

- 別の目的・別のユースケースで同じようなロジックが出てきても、無理に共通化しない
- 本当に同じロジックを使っているのであれば共通化すべきだが、似ているだけのロジックは別々に書く

## @Observable の使用禁止

- **`@Observable` は使用しない**。`@State` + `@Binding` で代替する
- どうしても `@Observable` を使わなければいけない理由がある場合は、その理由をコメントに書くこと
